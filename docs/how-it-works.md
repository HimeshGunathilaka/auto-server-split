# How it works

What the analysis does with each `"use client"` file, and where it stops. You don't need any of
this to use the tool: when it skips a file, the message and `--explain` say why.

## How it decides

1. **Module graph.** Every file the tsconfig covers, plus every other source and MDX file under the root (files the tsconfig excludes, `.js` without `allowJs`), with static imports, re-exports, `import()` and `next/dynamic`. Anything reachable from a `"use client"` module is client code.
2. **Candidates.** A `"use client"` file is a candidate only if every importer is a server module that renders its components as `<X />`, it exports only components and types, and nothing at module level behaves differently on the server. Importers outside the TypeScript project are checked without type information; when their usage can't be verified (an MDX file, `require()`), the file is skipped as `unsupported-pattern`. Because every importer is a Server Component, `memo()` and `forwardRef()` (when the ref goes unused) change nothing and are unwrapped.
3. **Client-only marking.** Hooks, event/ref/function props, browser globals, client-only packages (framer-motion, Radix, react-hook-form…), render nondeterminism (`Date.now()`, `Math.random()`, and date-library calls that read the current time, such as `formatDistanceToNow()`, `isToday()` or `dayjs()`), locale-dependent formatting (`toLocaleString()`, `Intl.*`, `localeCompare()`, unless the call names its locale and, for dates, its `timeZone`), and anything that can't be proven server-safe (unknown React packages, local exports that use hooks or browser APIs) are client-only, as are the imports and calls your [`rules`](configuration.md#rules) name. A local module is judged per export: it has to evaluate on the server (no client-only code runs on import, no named import of a client-only React API), and then only what the imported export uses must be server-safe, so `formatTitle` from a `utils.ts` that also exports `copyToClipboard()` stays on the server. Taint propagates through the component body to a fixpoint.
4. **Islands.** Elements that use client-only code are anchors. Anchors that share state merge (union-find), the island root is their lowest common ancestor, and an escape check grows the island until no client value is read outside it. In `.map()` lists, the mapped element becomes a per-item island, unless that would duplicate component-level state. Effects join the island whose state they use; effects that use no island's state move to an island that renders nothing, added as the last child of the returned element, where they run after everything the component renders, as before (unless an island's effect was declared after them, which would reorder the two, so the file is skipped). Static, non-trivial subtrees inside an island stay on the server as `children` ("donut"), and so does an element that renders a component held in a variable (`<LinkIcon />` with `const LinkIcon = link.icon`), since the component itself can't cross as a prop. In a file with several components, a non-exported helper component that is entirely interactive moves into the island file whole.
5. **Boundary.** Free variables become props and are proven serializable with the type checker (React's rules: primitives, plain objects, arrays, `Date`, `Map`, `Set`, typed arrays, Promises, JSX, Server Actions). Non-serializable helpers are copied into the island instead. When an island reads only some fields of an object, only those cross: `post={{ date: post.date }}`. That also lets an object that holds functions cross, when the island reads only its serializable fields.
6. **Rewrite.** magic-string range edits keep every untouched byte of the original. Imports move, are copied or are pruned, and the island file is generated in the original's quote, semicolon and indentation style. Prettier runs only when the project has a config and the original file is already formatted with it, so it can't rewrite lines the split didn't touch. Inserted lines and the island file use the original file's line ending (CRLF or LF, taken from its first line), with or without Prettier; a file that already mixes the two keeps its existing lines as they are.
7. **Self-check.** Before anything is reported or written, the output is typechecked in memory, re-analysed (no client code may remain in the server file), and every prop is re-checked. The typecheck allows no _new_ diagnostics: errors the file already had are tolerated, and diagnostics are compared by code and message. `.js`/`.jsx` files only get semantic checks when `checkJs` is on (never with a `jsconfig.json`), so for them this step is mostly a parse check.
8. **Measure.** The original file and the island file are bundled with esbuild (react/next external) and the gzip sizes compared. Per App Router route, the tool follows the page and its layouts through Server Components to the client modules the route loads before and after the changes, and adds up what leaves (sizes from the bundles, or from a Next.js analyzer snapshot with `--analyze-snapshot`). The estimate assumes every split the tool proposes for the project is applied (the run's own and those of the other `"use client"` files in `include`), so it doesn't depend on which paths you pass. The conservative number leaves out dependencies that other client modules would still ship, and a dependency that several splits remove together is counted once, divided between them: the output names those other splits ("assumes components/LintA.tsx is split too"). Splits below `minBytesSaved` are dropped until the rest still pass without them. If esbuild can't bundle a file, the saving is unknown: the file is skipped (`measure-failed`) unless `minBytesSaved` is 0, in which case it's split and labelled "saving not measured".
9. **Next pass.** Files skipped as `imported-by-client` are analysed again against the outputs so far (in memory, nothing is written in between) until a pass changes nothing. With `removeUnusedDirectives`, a file with no client-only code loses its directive after steps 1–2 and 7, and its saving is reported without applying the thresholds.

## Limitations

- **It's conservative.** On three well-known open-source apps, most `"use client"` files are skipped, because they are already genuinely interactive ([docs/benchmarks.md](benchmarks.md)). The tool pays off in codebases that put `"use client"` high in the tree.
- **Server vs browser rendering differences** stay a risk: timezone-dependent formatting moves from the browser to the server (`format(new Date(x), "PPP")` in the example above). The tool warns about the calls it recognises (`[timezone-dependent]`: date-fns formatting and calendar functions, dayjs/moment `.format()` without `.tz()`/`.utc()`, `Date`'s local getters, also inside functions imported from your own files) but doesn't refuse them, and other libraries go unnoticed. Calls it _can_ see are kept on the client: nondeterministic ones (`Date.now()`, `Math.random()`, `new Date()`, and date-fns, dayjs or moment calls that read the current time) and locale-dependent ones (`toLocaleString()`, `Intl.*`, `localeCompare()` without an explicit locale).
- **`bytesSaved` is project-wide**: code that any remaining client module imports counts as still shipped. The per-route numbers (`routes`) count a module as removed from a route when no client module on that route imports it any more, so a page can save more than `bytesSaved`. Without a snapshot, route sizes are estimates from esbuild bundles of the changed files; with `--analyze-snapshot` they're the Next.js analyzer's attribution (the islands' own size is still estimated).
- **Local modules must evaluate on the server.** A module that imports a client-only React API by name (`import { useState } from "react"`) or a client-only package stays client-only as a whole, because Next.js refuses that import anywhere in the server graph; per-export safety helps when the client-only code is inside function bodies.
- Third-party React packages are client-only unless they have a `"use client"` entry or are on the small built-in server-safe list. Unknown packages stay in islands.
- Not handled yet (they skip): class components, a `forwardRef` whose ref is used, render props, `next/dynamic`, Context providers (`--explain` suggests the extraction), runtime CSS-in-JS, statements other than declarations (a `let` only with the assignments right after it), hook calls and early returns in a component body, and effects that no element uses in a component with several returns. It never merges into an existing `X.client.tsx` (`outputExists: "alternate"` picks another name).
- `"use client"` barrels are reported (`--graph` lists the modules they re-export that don't need the directive) but not rewritten.
- Watch mode re-runs the whole analysis on each change; there's no editor language server yet.
- The ESLint rule caches the module graph and config per lint process, and can't load a config file that uses top-level await (rules are synchronous). It reads the config file the CLI finds by default, not one passed with `--config`.
- "Same rendered output" is enforced by the analysis rules, not re-checked on every run. The e2e suite checks it on two sample apps (identical server HTML, identical DOM after every interaction).
- Next.js only for now; framework specifics live in `src/frameworks/next.ts`. React Router's and TanStack Start's RSC support is still experimental (see [docs/prior-art.md](prior-art.md#other-rsc-frameworks)).
